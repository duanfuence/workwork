# Выкладка сайта на хостинг REG.RU

Сайт собирается и выкладывается сам: после слияния в ветку `main` GitHub проверяет сайт (те же проверки, что
перед каждым коммитом), собирает его с адресом `https://konturix.ru` и копирует готовые файлы в папку сайта
на хостинге. Выкладку можно запустить и вручную. Перед каждой выкладкой на сервере сохраняется резервная копия
папки сайта, а вернуть предыдущую версию можно одной кнопкой (раздел «Откат»). Решение и причины —
`docs/DECISIONS.md`, D-034 и D-035.

Пока вы не выполнили шаги 1–5 и не слили ветку в `main`, сайт никуда не выкладывается.

## Что нужно заранее

- Услуга «Хостинг» в REG.RU на Linux, тариф **не** «Хост-Лайт»: на нём нет доступа по SSH, а выкладка идёт по SSH.
- Домен `konturix.ru` привязан к этому хостингу, в панели хостинга создан сайт `konturix.ru`.
- Для сайта выпущен SSL-сертификат (в панели хостинга есть бесплатный). Без него `https://konturix.ru`
  не откроется, а файл настроек сайта отправляет всех посетителей на `https`.
- На сервере есть команда `sha256sum` (пакет coreutils, на Linux-хостинге обычно есть). Проверить при входе
  по SSH (шаг 1): `printf abc | sha256sum` должна вывести `ba7816bf…20015ad`. Без неё выкладка и восстановление
  остановятся на первой проверке, ничего не изменив: по SHA-256 выкладка узнаёт одинаковые копии и проверенную
  версию.

## Шаг 1. Данные из кабинета REG.RU

1. Войдите в личный кабинет REG.RU, откройте **Хостинг** и выберите услугу.
2. Откройте вкладку **«Доступы»**. Там есть всё для входа по SSH:
   - **IP-адрес сервера** — например, `31.31.196.123`;
   - **логин** — вида `u1234567`;
   - **пароль** — понадобится один раз, чтобы добавить ключ (шаг 2).
3. Узнайте **корневую папку сайта** — куда класть файлы:
   - откройте панель управления хостингом (ссылка — на той же вкладке «Доступы»);
   - в разделе **«Сайты»** найдите `konturix.ru`, столбец **«Корневая директория»** (или раздел «Домены»,
     столбец «Корень документа»). Там путь от вашей папки, например `www/konturix.ru`;
   - полный путь — с началом `/var/www/u1234567/data/` (в панели ispmanager; вместо `u1234567` — ваш логин):
     `/var/www/u1234567/data/www/konturix.ru`.
   - Для konturix.ru это **`/var/www/u3703509/data/www/konturix.ru`** — и только в эту папку скрипты выкладки
     согласны копировать (путь записан в `scripts/deploy-lib.sh`). Если в панели путь другой, скажите мне:
     его нужно поменять в коде, а не только в секрете.
4. Проверьте путь: на компьютере откройте «Терминал» (на Windows — PowerShell) и выполните, подставив свои данные:

   ```
   ssh u1234567@31.31.196.123
   ```

   При первом входе программа покажет «отпечаток» сервера и спросит, доверять ли ему, — ответьте `yes`. Введите
   пароль с вкладки «Доступы» (при вводе он не отображается). Затем:

   ```
   ls /var/www/u1234567/data/www/konturix.ru
   ```

   Команда должна показать содержимое папки сайта (или ничего, если она пуста), а не «No such file or directory».
   Выйти — `exit`.

> **Важно.** Выкладка приводит папку сайта к содержимому сборки: всё, чего в сборке нет, из папки удаляется
> (кроме служебной папки `.well-known` — она нужна для SSL-сертификата — и стилей и скриптов предыдущей версии
> в `/_astro/`). Перед первой выкладкой содержимое папки сохраняется в резервную копию `initial`, которая не
> удаляется автоматически, но если в папке лежит что-то нужное (старый сайт, ваши файлы), заберите это заранее.

## Шаг 2. Ключ для выкладки

Ключ — пара файлов: закрытый (отдаётся GitHub, никому больше) и открытый (кладётся на хостинг). С ключом
GitHub входит на хостинг без пароля, а пароль хостинга нигде не хранится. Создайте отдельный ключ только для
выкладки — не используйте свой личный.

1. На компьютере в «Терминале» (Windows — PowerShell):

   ```
   ssh-keygen -t ed25519 -C "github-deploy-konturix" -f konturix_deploy -N ""
   ```

   В текущей папке появятся два файла: `konturix_deploy` (закрытый ключ) и `konturix_deploy.pub` (открытый).
   `-N ""` — ключ без пароля: GitHub не сможет его ввести.
   В Windows PowerShell пустой пароль пишется так: `-N '""'`; если программа всё же спросит пароль ключа —
   дважды нажмите Enter.

2. Положите открытый ключ на хостинг:

   ```
   ssh-copy-id -i konturix_deploy.pub u1234567@31.31.196.123
   ```

   Команда попросит пароль хостинга один раз. Если `ssh-copy-id` нет (на Windows), сделайте то же вручную: войдите
   по SSH, как в шаге 1, и выполните (вместо `ВСТАВЬТЕ_КЛЮЧ` — всё содержимое файла `konturix_deploy.pub`,
   одной строкой):

   ```
   mkdir -p ~/.ssh && chmod 700 ~/.ssh
   echo "ВСТАВЬТЕ_КЛЮЧ" >> ~/.ssh/authorized_keys && chmod 600 ~/.ssh/authorized_keys
   ```

3. Проверьте вход по ключу — пароль спрашиваться не должен:

   ```
   ssh -i konturix_deploy u1234567@31.31.196.123 "echo вход по ключу работает"
   ```

**Если хостинг ключ не принимает** (в шаге 3 всё равно спрашивается пароль): проверьте права (`~/.ssh` — 700,
`~/.ssh/authorized_keys` — 600) и что ключ записан одной строкой. Если не помогло — напишите мне: выкладка умеет
входить и по паролю, но это хуже (пароль хостинга даёт полный доступ и меняется при сбросе), поэтому в workflow
вход по паролю сейчас не подключён.

## Шаг 3. Строка «known_hosts» — подпись сервера

GitHub должен быть уверен, что подключается именно к вашему серверу, а не к подставному: выкладка всегда
сверяет подпись сервера и без неё не подключится. Подпись нужно получить один раз и сохранить в секрет
`SSH_KNOWN_HOSTS`.

1. Узнайте подпись — с **тем же адресом**, что записан в секрете `SSH_HOST` (IP или имя сервера):

   ```
   ssh-keyscan -t ed25519 31.31.196.123
   ```

   Команда выведет строку вида `31.31.196.123 ssh-ed25519 AAAAC3Nza…`. Если сервер слушает не порт 22, добавьте
   `-p ПОРТ` — строка тогда начнётся с `[31.31.196.123]:ПОРТ`, так и нужно.

2. Убедитесь, что подпись настоящая, — сравните отпечатки:

   ```
   ssh-keyscan -t ed25519 31.31.196.123 | ssh-keygen -lf -
   ssh-keygen -lF 31.31.196.123
   ```

   Первая команда показывает отпечаток только что полученной строки, вторая — отпечаток, который вы приняли при
   первом входе в шаге 1 (он хранится в `~/.ssh/known_hosts` на вашем компьютере). Строки `SHA256:…` должны
   совпасть. Если не совпадают — не сохраняйте строку и напишите в поддержку REG.RU.

3. Если `ed25519` сервер не выдаёт (команда ничего не вывела), уберите `-t ed25519` и сохраните все строки,
   которые она выведет.

Строку (или строки) целиком, без изменений, вы сохраните в секрет `SSH_KNOWN_HOSTS` в шаге 4. Если адрес в
`SSH_HOST` и в строке разный (в одном IP, в другом имя), подключение будет отклонено.

## Шаг 4. Секреты и переменная в GitHub

Откройте репозиторий на GitHub → **Settings** → **Secrets and variables** → **Actions**.

**Секреты** (вкладка **Secrets** → **New repository secret**). Четыре уже добавлены — не переименовывайте их;
добавьте пятый, `SSH_KNOWN_HOSTS`:

| Секрет            | Что в нём                                                                                           | Как его видит выкладка |
| ----------------- | --------------------------------------------------------------------------------------------------- | ---------------------- |
| `SSH_HOST`        | IP-адрес сервера из шага 1, например `31.31.196.123`                                                | `DEPLOY_HOST`          |
| `SSH_USER`        | логин, например `u1234567`                                                                          | `DEPLOY_USER`          |
| `SSH_TARGET`      | ровно `/var/www/u3703509/data/www/konturix.ru` — без пробелов и без `/` на конце                    | `DEPLOY_PATH`          |
| `SSH_PRIVATE_KEY` | всё содержимое файла `konturix_deploy` (закрытый ключ), от `-----BEGIN` до `-----END…` включительно | `DEPLOY_SSH_KEY`       |
| `SSH_KNOWN_HOSTS` | строка (или строки) из шага 3                                                                       | `DEPLOY_KNOWN_HOSTS`   |

В журнале выкладки ошибки называют секреты по правому столбцу: «Не задан секрет DEPLOY_HOST» означает, что пуст
`SSH_HOST`, и так далее. `SSH_TARGET` сверяется с разрешённым путём символ в символ: любой другой путь (папка
другого сайта, домашняя папка, путь со слэшем на конце или с `..`) выкладка отклонит ещё до подключения к серверу.

**Переменная** (вкладка **Variables** → **New repository variable**) — именно на уровне репозитория, а не окружения:
её читает и шаг проверок, который работает без окружения.

| Переменная    | Значение                                                                              |
| ------------- | ------------------------------------------------------------------------------------- |
| `SITE_URL`    | `https://konturix.ru` — ровно так: с `https://`, без `www`, без слэша и пути на конце |
| `DEPLOY_PORT` | только если у хостинга не стандартный порт SSH; обычно не нужна (порт 22)             |

С неверным `SITE_URL` (`http://…`, со слэшем или путём на конце) сборка остановится с объяснением; с пустым —
выкладка остановится на первом шаге «Адрес сайта задан».

Секреты GitHub не показывает ни вам, ни в журналах выкладки — их можно только заменить. После того как
секрет добавлен, файл `konturix_deploy` с компьютера можно удалить (или хранить в надёжном месте).

## Шаг 5. Окружение production

Шаг выкладки работает в окружении GitHub **production**. Окружение ограничивает, откуда можно выкладывать,
и может требовать вашего подтверждения перед каждой выкладкой.

1. **Settings** → **Environments** → **New environment**, имя — `production` (ровно так, строчными буквами) →
   **Configure environment**. Если окружение уже появилось само (GitHub создаёт его при первом запуске), просто
   откройте его.
2. **Deployment branches and tags** → выберите **Selected branches and tags** → **Add deployment branch or tag
   rule** → `main`. Выкладка из любой другой ветки будет отклонена.
3. По желанию — **Required reviewers**: отметьте себя. Тогда каждая выкладка будет ждать, пока вы нажмёте
   **Review deployments** → **Approve and deploy** на странице запуска.
4. Секреты можно оставить в репозитории (шаг 4) — шаг выкладки их видит. Если хотите, чтобы SSH-секреты были
   доступны только выкладке: в окружении нажмите **Add environment secret** и добавьте те же пять секретов с теми
   же именами, затем удалите их из репозитория. Переменную `SITE_URL` оставьте на уровне репозитория (шаг 4).

После первой выкладки на главной странице репозитория справа появится блок **Deployments** со ссылкой на сайт.

## Шаг 6. Выкладка

- **Автоматически** — после слияния ветки в `main`: на GitHub откройте **Actions** → **Deploy**, там появится
  запуск.
- **Вручную** — **Actions** → **Deploy** → **Run workflow** → ветка `main` → **Run workflow**. Ручной запуск
  из другой ветки только проверяет и собирает сайт, но не выкладывает.

Как понять, что выкладка прошла: у запуска зелёная галочка и у обоих шагов — «Проверки и сборка с адресом сайта»
и «Выкладка на хостинг». В журнале шага «Выкладка и проверка сайта»: «Способ копирования: rsync» (или «sftp»),
«Резервная копия: konturix-…tar.gz (…)», «Копирование завершено. Проверка сайта…»,
`https://konturix.ru/ → 200, отдаётся ожидаемая версия главной страницы` и в конце «Готово: сайт выложен и прошёл
проверку — эта версия отмечена как последняя проверенная». Если галочка красная — откройте красный шаг: в строке
с ошибкой написано, что не так (раздел «Если что-то не так»).

Проверки занимают около 10 минут, копирование — меньше минуты. Одновременно идёт только одна выкладка: если
слить два изменения подряд, вторая выкладка дождётся первой.

## Шаг 7. Проверка после первой выкладки

Откройте в браузере (лучше в режиме «инкогнито») и проверьте:

- [ ] `https://konturix.ru` — открывается главная, в адресной строке замок.
- [ ] `http://konturix.ru` → сразу `https://konturix.ru/`.
- [ ] `https://www.konturix.ru` и `http://www.konturix.ru` → сразу `https://konturix.ru/`.
- [ ] `https://konturix.ru/kalkulyatory/oboi` (без слэша) → `https://konturix.ru/kalkulyatory/oboi/`.
- [ ] `https://konturix.ru/robots.txt` — текст со строкой `Sitemap: https://konturix.ru/sitemap.xml`.
- [ ] `https://konturix.ru/sitemap.xml` — список из 8 адресов на `https://konturix.ru/…`.
- [ ] На странице калькулятора (например, обоев) правый клик → «Просмотр кода страницы», найдите `canonical`:
      `<link rel="canonical" href="https://konturix.ru/kalkulyatory/oboi/">`.
- [ ] `https://konturix.ru/net-takoy-stranitsy/` — страница «Страница не найдена». Код ответа 404 видно
      в инструментах разработчика браузера (вкладка «Сеть») или командой ниже.

То же из терминала (код ответа и куда перенаправляет):

```
curl -sI http://www.konturix.ru/kalkulyatory/oboi | head -3
curl -sI https://konturix.ru/net-takoy-stranitsy/ | head -1
```

Первая команда — `301` и `location: https://konturix.ru/kalkulyatory/oboi/`, вторая — `404`.

После проверки добавьте сайт в Яндекс Вебмастер и Google Search Console и отправьте там
`https://konturix.ru/sitemap.xml` (docs/SEO_STRATEGY.md).

## Резервные копии

Перед каждой выкладкой (и перед каждым восстановлением) скрипт сохраняет всю папку сайта в архив на сервере —
**до** того, как что-либо в ней изменится:

- где: `/var/www/u3703509/data/konturix-backups/` — домашняя папка хостинга, вне папок сайтов, по адресу сайта
  не открывается; права — только для вашего пользователя. Если на этом месте окажется символическая ссылка
  или файл, выкладка и восстановление останавливаются до любых изменений;
- имя: `konturix-ГГГГММДД-ЧЧММСС-метка.tar.gz`, время — UTC; метка — первые 7 знаков коммита, который
  выкладывался (`restore` — копия перед восстановлением, `manual` — запуск не из GitHub, `initial` — самая
  первая копия);
- если копию создать не удалось (нет места, нет прав, файл не читается), выкладка **останавливается** с ошибкой
  «Не удалось создать резервную копию», и в папке сайта ничего не меняется.

### Последняя хорошая версия

**Хорошая (проверенная) версия — только та, что прошла проверку сайта после выкладки**: главная страница по адресу
`SITE_URL` ответила 200 и совпала байт в байт с собранной. Выкладка проходит три состояния, и они не смешиваются:

1. **резервная копия создана** — копия того, что было на сайте до выкладки;
2. **копирование завершено** — файлы новой версии на сервере, но сайт ещё не проверен;
3. **проверка пройдена** — только теперь версия считается проверенной.

Состояние 3 ставит сам скрипт выкладки сразу после успешной проверки, в том же процессе — отдельного шага или
кнопки «отметить проверенной» нет. Если проверка не прошла, выкладку прервали или запись состояния не удалась,
версия остаётся непроверенной, а запуск — красным. Восстановление (Restore) никогда не отмечает версию
проверенной.

Работающая проверенная версия попадает в резервную копию перед следующей операцией — эта копия отмечается как
«проверенная версия». Самая новая такая копия — **последняя хорошая версия**: её восстанавливает Restore
с `last-good`.

### Какие копии хранятся

- **последние 5** — более старые удаляются автоматически, кроме трёх случаев ниже;
- **первая копия** (метка `initial`) — то, что лежало в папке сайта до первой выкладки (заглушка хостинга или
  старый сайт). Автоматически не удаляется никогда; удалить её можно только вручную;
- **последняя хорошая версия** — самая новая проверенная копия. Не удаляется, сколько бы неудачных выкладок ни
  было после неё: неудачные (не прошедшие проверку, прерванные) выкладки дают только непроверенные копии;
- **копия, из которой идёт восстановление** — на время этого восстановления не удаляется, даже если она самая
  старая.

Если файлы сайта не изменились с самой новой копии (например, неудачную выкладку повторяют снова и снова),
новая копия не создаётся — используется та же. Список с пометками («проверенная версия», «последняя
проверенная — last-good», «первая, не удаляется») показывает Restore с `list`. Если в папке сайта до первой выкладки есть что-то ценное,
всё равно скачайте это себе заранее.

Скачать копию к себе на компьютер (подставьте имя из списка):

```
scp -i konturix_deploy u3703509@31.31.196.123:konturix-backups/konturix-20261104-120000-abc1234.tar.gz .
```

## Прежние CSS и JS

Стили и скрипты сайта лежат в `/_astro/` под именами с хешем: у новой версии — новые имена. Выкладка не удаляет
файлы предыдущей версии сразу: посетитель, открывший страницу за минуту до выкладки, продолжит получать её стили
и скрипты. Политика: в `/_astro/` хранятся файлы **текущей и предыдущей** версии; более старые удаляются в конце
следующей выкладки. Список файлов работающей версии — `~/konturix-backups/.assets-live`. Если его нет (первая
выкладка или после ручного восстановления), выкладка ничего из `/_astro/` не удаляет.

## Откат: восстановление из резервной копии

**Кнопкой в GitHub** (после слияния в `main`): **Actions** → **Restore** → **Run workflow** → ветка `main`,
в поле «Какую копию»:

- `latest` (по умолчанию) — самая новая копия, то есть состояние **до последней операции** (выкладки или
  восстановления). Если последняя выкладка не прошла проверку или прервалась и её запускали повторно, самая
  новая копия может хранить непроверенную версию — тогда выберите `last-good`;
- `last-good` — **последняя хорошая версия**: самая новая копия с пометкой «проверенная версия» (прошла
  проверку сайта после выкладки);
- `list` — только показать список копий (новые сверху, с размером и пометками) и ничего не менять;
- имя копии, например `konturix-20261104-120000-abc1234.tar.gz`, — конкретная копия из списка.

Что происходит: копия скачивается на сервер GitHub и проверяется (архив цел, внутри только папка сайта, без
ссылок и путей с `..`); затем сохраняется копия **текущего** состояния (метка `restore`) и папка сайта приводится
к содержимому выбранной копии теми же тремя этапами, что и выкладка (раздел «Если выкладка оборвалась»); в конце —
проверка, что сайт отдаёт главную страницу из копии. Восстановление тоже можно отменить: следующий запуск
с `latest` вернёт состояние до него. Если в окружении `production` включено ручное подтверждение, Restore тоже
его ждёт.

Восстановление меняет только файлы на хостинге, не ветку `main`: следующее слияние снова выложит `main`. Чтобы
откат был окончательным, отмените изменение и в коде (**Revert** у слитого PR или `git revert`) — тогда выкладка
`main` и будет откатом.

**Вручную по SSH** (если GitHub недоступен; нужен rsync на сервере — `command -v rsync` что-то выводит). Это
запасной способ: он тоже не атомарный и удаляет прежние CSS и JS сразу.

```
ssh -i konturix_deploy u3703509@31.31.196.123
ls -1 ~/konturix-backups/
# сначала копия текущего состояния — чтобы можно было вернуться:
tar -czf ~/konturix-backups/konturix-$(date -u +%Y%m%d-%H%M%S)-manual.tar.gz -C ~/www konturix.ru
# восстановление выбранной копии (вместо ИМЯ — имя из списка):
rm -rf ~/restore-tmp && mkdir ~/restore-tmp
tar -xzf ~/konturix-backups/ИМЯ -C ~/restore-tmp
rsync -a --delete-delay --delay-updates --exclude=/.well-known/ ~/restore-tmp/konturix.ru/ ~/www/konturix.ru/
rm -rf ~/restore-tmp
# следующая выкладка не будет удалять CSS и JS восстановленной версии:
rm -f ~/konturix-backups/.assets-live
```

## Если выкладка оборвалась

Выкладка и восстановление **не атомарны**: файлы встают на место по одному, и если процесс копирования
прервётся (обрыв связи, остановка запуска по времени, аварийное завершение процесса на сервере — например, по
лимитам хостинга или при перезагрузке), сайт может оказаться **частично обновлённым**: часть страниц новая, часть
прежняя. Порядок копирования уменьшает вред такого сбоя:

1. **Этап 1** — всё, кроме страниц и файлов управления сайтом (`.htaccess`, `robots.txt`, `sitemap.xml`): новые
   стили и скрипты, шрифты, картинки. Прежние страницы их не используют — сайт работает в прежнем виде.
2. **Этап 2** — страницы и файлы управления. Каждая новая страница встаёт на место, когда её стили и скрипты уже
   на сервере, а прежние ещё не удалены.
3. **Этап 3** — удаление устаревших файлов (кроме `/_astro/`, см. «Прежние CSS и JS») и отметка, что операция
   завершена.

Как это выглядит при каждом способе копирования:

- **rsync:** на этапах 1 и 2 файлы сначала докачиваются во временные папки `.~tmp~`, а в конце этапа
  переименовываются на место по одному. Обрыв связи во время докачки — файлы этапа не меняются. Аварийное
  завершение процесса rsync на сервере во время переименований — часть файлов этапа уже новая, часть прежняя.
- **SFTP (если на сервере нет rsync):** файл пишется во временный `.in.*`, затем прежний файл **удаляется**
  и временный **переименовывается** на его место. Между этими двумя действиями файла нет (доли миллисекунды);
  обрыв ровно в этот момент оставит сайт без этого файла (например, страница ответит 404) до повторного запуска.
  Обрезанных файлов на месте настоящих не бывает.

Проверено на тестовом сервере (раздел «Как устроено и как проверялось»): после сбоя на любом этапе каждый файл
на сервере — целиком прежний или целиком новый, и у каждой страницы на месте её стили и скрипты. Исключение —
окно «удалить → переименовать» у SFTP: его тестом не поймать.

Временные `.~tmp~` и `.in.*` по адресу сайта не открываются (404, `.htaccess`). Что делать:

1. Запустить выкладку ещё раз (**Actions** → **Deploy** → **Run workflow** → `main`, или **Re-run jobs**
   у запуска) — обычно этого достаточно: она докопирует и уберёт временные файлы.
2. Если сайт работает неправильно, а повтор не помогает, — откатить: **Restore** с копией, которую назвало
   сообщение об ошибке («копия konturix-…»), или с `last-good` — последней хорошей версией.

## Как устроено и как проверялось

- `.github/workflows/deploy.yml` — две задачи: «Проверки и сборка» (`npm run check` и `ui:check` с `SITE_URL` из
  переменной) и «Выкладка» (только после успешных проверок, только из `main`, в окружении `production`; секреты
  `SSH_*` передаются только в шаг «Выкладка и проверка сайта» и только под именами `DEPLOY_*`). В этом шаге
  `scripts/deploy.sh` копирует сайт, сравнивает главную по адресу сайта со сборкой байт в байт
  (`scripts/check-site.sh`) и только после успешной проверки отмечает версию проверенной.
- `.github/workflows/restore.yml` — откат из резервной копии: только вручную, только `main`, окружение
  `production`, общая очередь с выкладкой.
- `scripts/deploy-lib.sh` — общая часть: единственный разрешённый путь, вход с проверкой подписи сервера,
  резервная копия и её хранение, копирование в три этапа (rsync или SFTP), очистка устаревших CSS/JS.
  `scripts/deploy.sh` — выкладка: полнота сборки (`index.html`, `404.html`, `.htaccess`, `robots.txt`,
  `sitemap.xml`, не меньше 2 страниц) и путь — до подключения к серверу, затем копия, затем копирование.
  `scripts/restore.sh` — восстановление.
- `public/.htaccess` — настройки сервера: один переход на `https://` без `www` и со слэшем, страница 404, кэш,
  сжатие, заголовки безопасности, временные файлы копирования — 404.

Проверено в среде разработки (не на REG.RU):

- `scripts/deploy-remote.test.mjs` (в `npm test`): сценарий на сервере (тот же POSIX sh) на временных папках
  с подменённой `sha256sum` — нет команды, ошибка, пустой, мусорный и неверный результат, ошибка только на
  файлах сайта: проверка перед копией отвечает `no-sha256sum`, копия, `finish` и `verify` завершаются ошибкой,
  архив и статус `verified` не появляются; отпечаток: одинаковое содержимое — тот же, другое содержимое того
  же размера и переименование — другой, `.well-known` не влияет, испорченный `.sum` не даёт ложного совпадения.
- `scripts/deploy.test.mjs` (в `npm test`, на каждый push): 29 опасных значений `SSH_TARGET` для выкладки

- `scripts/deploy-e2e.sh` (workflow **Deploy check** при изменении файлов выкладки) — на настоящем SSH-сервере
  с пользователем `u3703509` и той же папкой сайта: выкладка rsync и SFTP; прежние CSS/JS хранятся ровно одну
  выкладку; сбой копии, файл или ссылка вместо каталога копий — остановка без изменений; сбой каждого из трёх
  этапов rsync и повторная выкладка; аварийное завершение rsync на сервере посреди финального переноса — сайт
  частично обновлён, но у каждой страницы на месте её стили и скрипты; обрыв связи на каждом проходе SFTP;
  последняя хорошая версия: B прошла проверку, C шесть раз выложена с упавшей проверкой — B остаётся последней
  проверенной (копий +1, не +6), ещё шесть неудачных выкладок разных версий не вытесняют B; успешная C становится
  последней проверенной; сбой между копированием и проверкой и между проверкой и записью статуса — версия не
  отмечена; одинаковые выкладки не плодят копий; восстановление самой старой копии (она не удаляется), два
  восстановления подряд, `last-good` (Restore не добавляет проверенных версий), первая копия; отказ на подложенной
  копии с путём вне папки сайта; вход по паролю; ключ, пароль и адрес сервера в журнал не попадают; файл
  в домашней папке вне сайта не тронут.
- `.htaccess` — на Apache 2.4 с `AllowOverride All`, по `http` и `https`: каждый неканонический адрес (http, www,
  без слэша, их сочетания, с параметрами) — одним переходом 301 на канонический; заголовок `X-Forwarded-Proto:
https` не вызывает перехода; несуществующий адрес, папки без страницы и временные файлы копирования — 404;
  `.well-known` отдаётся; кэш, сжатие, кодировка и заголовки — как описано в D-034.
- Ручное восстановление по SSH (команды выше) — на том же тестовом сервере.

Не проверено до первой настоящей выкладки: есть ли на сервере REG.RU `sha256sum` (если нет — выкладка
остановится на первой проверке, ничего не изменив) и rsync (если нет, выкладка сама перейдёт на SFTP), принимает
ли хостинг ключ, все ли строки `.htaccess` разрешены на нём и хватает ли места под копии
(сайт — меньше 1 МБ, копий обычно 5–7).

Чего нет и на этом хостинге не будет без отдельной проверки: атомарного переключения версий (новая версия
в отдельной папке и мгновенная подмена ссылкой). Папку сайта задаёт панель хостинга, а поддерживает ли
веб-сервер REG.RU папку сайта в виде символической ссылки, неизвестно (D-035).
