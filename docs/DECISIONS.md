# Журнал решений

Формат: номер, дата, решение, причина, последствия.

## D-001 · 2026-10-24 · Astro + TypeScript, статическая генерация

**Решение:** сайт на Astro с TypeScript, `output: 'static'`; интерактивность — только точечными скриптами.
**Причина:** SEO-ориентированный сайт с отдельными страницами калькуляторов; статика быстрая и бесплатно хостится.
**Последствия:** нет серверной части; БД, регистрация и личные кабинеты требуют отдельного решения.

## D-002 · 2026-10-24 · URL калькуляторов `/kalkulyatory/<slug>/`

**Решение:** плоская схема на транслите, не зависящая от категории; `trailingSlash: 'always'`.
**Причина:** перенос калькулятора между категориями не должен ломать URL; транслит читаем в выдаче.

## D-003 · 2026-10-24 · Каталог как единый типизированный источник

**Решение:** `src/data/calculators.ts` + `catalog.types.ts`; ссылки — только для `status: 'available'`.
**Причина:** нельзя показывать ссылки на несуществующие страницы; главная, поиск и sitemap используют одни данные.

## D-004 · 2026-10-24 · Версии инструментов под Node.js 22.22.0

**Решение:** зафиксированы точные версии: astro 7.4.1, typescript 5.9.3, @astrojs/check 0.9.12,
vitest 5.0.5, eslint 10.13.0, typescript-eslint 8.72.0, eslint-plugin-astro 1.7.0, prettier 3.9.10,
prettier-plugin-astro 1.1.2. `.nvmrc` = 22.22.0, `engines.node` ≥ 22.22.0.
**Причина:**

- astro 7.4.2 требует Node ≥ 22.23.4, а в облачной среде Node 22.22.0;
- eslint-plugin-astro 2.x/3.x требуют Node ≥ 22.22.3;
- TypeScript 7 не поддерживается @astrojs/check (^5 || ^6) и typescript-eslint (< 6.1);
- ESLint 9 помечен как неподдерживаемый, поэтому ESLint 10.
  **Последствия:** при обновлении Node в среде можно поднять astro и eslint-plugin-astro.

## D-005 · 2026-10-24 · Без UI-фреймворков, системные шрифты, собственные CSS-токены

> Часть про системные шрифты заменена решением D-029 (свои веб-шрифты Onest и JetBrains Mono).

**Решение:** без React/Vue/Tailwind и веб-шрифтов; CSS-переменные в `tokens.css`.
**Причина:** минимальный вес страниц, мало зависимостей; задачам этапа хватает встроенных средств Astro.

## D-006 · 2026-10-24 · Playwright — локальный скрипт, не зависимость

**Решение:** `scripts/ui-check.mjs` использует предустановленный в среде Playwright; в CI не входит.
**Причина:** не тянуть браузеры (~сотни МБ) в зависимости и CI на этапе каркаса.
**Пересмотреть:** на этапе 4 (подготовка к публикации) — добавить e2e в CI.
**Заменено:** D-020 (2026-10-26) — Playwright в devDependencies, `ui:check` в CI.

## D-007 · 2026-10-24 · Поиск по каталогу на клиенте

**Решение:** поиск фильтрует уже отрисованные карточки по индексу, собранному при сборке; логика общая с тестами.
**Причина:** каталог маленький; не нужен поисковый сервис или библиотека. Без JS поле поиска скрыто.

## D-008 · 2026-10-24 · Телеметрия Astro отключена

**Решение:** `ASTRO_TELEMETRY_DISABLED=1` в npm-скриптах `dev`, `build`, `preview`, `typecheck`, в `env` CI
и при запуске `astro preview` из `scripts/ui-check.mjs`.
**Причина:** в Astro 7.4.1 анонимная телеметрия включена по умолчанию и записывается даже в CI
(проверено: без переменной `astro build --verbose` пишет события, с переменной — `telemetry has been disabled`).
В `astro.config` нет настройки для отключения.
**Последствия:** префикс переменной работает в POSIX-оболочках (Linux, macOS, облачная среда, CI). В Windows
cmd нужно выполнить `npx astro telemetry disable` (сохраняется глобально). Прямой вызов `npx astro …` без
переменной телеметрию не отключает — использовать npm-скрипты. Сборки этапа 1 в облачной среде шли без переменной.

## D-009 · 2026-10-24 · Расчёты в целых миллиметрах

**Решение:** размеры переводятся в целые миллиметры (`Math.round`), деление с округлением — целочисленное (`ceilDiv`).
**Причина:** двоичные дроби дают ошибку на границе: 2 · (2,22 + 5,73) / 0,53 = 30,000000000000004 → 31 полоса вместо 30.
**Последствия:** точность ввода размеров — 1 мм. Правило распространяется на будущие калькуляторы.

## D-010 · 2026-10-24 · Проёмы в калькуляторе обоев — гарантированная экономия

**Решение:** проём уменьшает число полных полос на `max(0, ⌊ширина / ширина рулона⌋ − 1)`; короткие куски
над/под проёмом раскладываются по остаткам рулонов, при нехватке — добавляются рулоны.
**Причина:** положение проёма относительно стыков неизвестно; вычитание площади проёмов дало бы правдоподобный,
но заниженный результат. Ошибка в сторону запаса безопаснее нехватки рулона из той же партии.
**Последствия:** узкие двери (уже двух полос) расход не уменьшают; при удачном расположении проёмов реальный
расход может быть немного меньше. Подробно — `docs/calculators/WALLPAPER.md`.
**Уточнено в D-013/D-014 (этап 2.1):** при раппорте кусок под окном берётся с запасом на совмещение;
если кусок не короче полосы, экономии нет; итог — меньший из планов с проёмами и без.

## D-011 · 2026-10-24 · FAQ без микроразметки FAQPage, хлебные крошки без JSON-LD до появления домена

**Решение:** FAQ — обычный HTML (h3 + p), всегда раскрыт. JSON-LD (`BreadcrumbList`) добавить вместе с доменом.
**Обновлено 2026-10-26:** `BreadcrumbList` выводится при заданном `SITE_URL` на страницах калькуляторов. Цепочка —
одна функция `calculatorCrumbs` (`src/lib/breadcrumbs.ts`); видимые крошки и JSON-LD строит из одних `items`
компонент `Breadcrumbs.astro`, поэтому разойтись они не могут. Адреса абсолютные; у текущей страницы — canonical;
у «Калькуляторы» — страница каталога `https://домен/kalkulyatory/` (с 2026-10-26, раньше — якорь `/#catalog`);
у самого каталога — своя цепочка «Главная → Калькуляторы» (`catalogCrumbs`). `FAQPage` по-прежнему не используется —
причина ниже не изменилась.
**Причина:** для JSON-LD нужны абсолютные URL, а `site` ещё не задан; расширенные сниппеты FAQ в Google
с 2023 года показываются только авторитетным государственным и медицинским сайтам. Видимый текст полезен
пользователю и индексируется независимо от разметки.

## D-012 · 2026-10-24 · Ввод чисел через `type="text"` с `inputmode`

**Решение:** поля калькулятора — `type="text"` с `inputmode="decimal"`/`numeric`, разбор в `parseDecimal`.
**Причина:** `type="number"` по-разному обрабатывает запятую в разных браузерах и локалях, а при неверном вводе
отдаёт пустую строку — нельзя отличить «пусто» от «ошибка». Своя проверка даёт понятные сообщения на русском.

## D-013 · 2026-10-25 · Обои: полосы по стенам и подгонка рисунка в начале рулона

**Решение:** число полос — `2·⌈L/w⌉ + 2·⌈W/w⌉` (каждая стена от угла); при раппорте в начале каждого рулона
резервируется до одного раппорта на совмещение рисунка: `k = ⌊(R − r − (H + t)) / S⌋ + 1`; кусок под окном
при раппорте — `+ r`.
**Причина:** аудит этапа 2.1 показал, что версия 1 могла занижать расход: `⌈P/w⌉` молча предполагал перенос
углового обрезка на соседнюю стену без нахлёста, а `⌊R/S⌋` — что каждый рулон начинается точно с нужной фазы.
Пользователь просил выбирать консервативный вариант, если допустимы разные.
**Последствия:** типичные результаты выросли на 0–1 рулон (4 × 3 × 2,5 м: 9 → 10). Аккуратный мастер, переносящий
угловые обрезки, может уложиться в меньшее число — это указано на странице.

## D-014 · 2026-10-25 · Проёмы никогда не увеличивают расход обоев

**Решение:** считаются два гарантированных плана — с экономией на проёмах и без неё — и выбирается меньший;
колонка, у которой куски не короче полосы, экономией не считается.
**Причина:** раскладка кусков отдельно от полос может требовать больше рулонов, чем полные полосы.

## D-015 · 2026-10-25 · Общий механизм форм калькуляторов

**Решение:** общий код вынесен в три места: `src/lib/form.ts` (чистый разбор полей), `src/client/calculator-form.ts`
(поведение в браузере: ошибки, сводка, фокус, состояния, пересчёт, сброс), `CalculatorResult.astro` (разметка
блока результата). Страница калькулятора передаёт `fields`, `evaluate` и `render`.
**Причина:** этот код одинаков для любого калькулятора и уже проверен Playwright на обоях; математика и состав
результата у каждого калькулятора свои.
**Не делалось намеренно:** описание полей конфигурацией и генерация формы — пока не нужно, усложнило бы разметку.
Модуль `client/` не покрыт unit-тестами (нужна DOM-среда — отдельная зависимость); его поведение проверяет
`npm run ui:check`.

## D-016 · 2026-10-25 · Ламинат: план раскладки по рядам, площадь — справочно

**Решение:** основной результат калькулятора ламината — число досок по построенному плану раскладки по рядам
для **выбранных пользователем** направления и схемы смещения (1/2, 1/3, «от обрезка»). Профиль замка: из доски
не больше одного начального (правая часть) и одного конечного (левая часть) отрезка; доски для выбранных рядов
считаются точно: целые + начала + концы − пары. Минимальный отрезок и минимальное смещение берутся из инструкции,
по умолчанию 400 мм (строгое значение). Расчёт по площади показывается справочно, с тем же запасом.
Процентный запас добавляется к доскам плана и объясняется как запас на брак и ошибки, а не на подрезку.
**Причина:** для выбранной раскладки площадь может быть заметно меньше плана — в контрольных примерах до 7 досок
(К5) и на одну упаковку (К13: 4,0 × 3,5 м вдоль длины — 57 досок = 8 упаковок против 53 = 7 по площади).
Это свойство раскладки, а не комнаты: та же комната поперёк по схеме 1/3 — 56 досок = 7 упаковок.
**Последствия:** калькулятор **не определяет глобальный минимум покупки** — не перебирает направления, схемы
и стартовые стены; результат честен только для выбранной раскладки. План не учитывает препятствия, зазор и пропил
(допущения в `docs/calculators/LAMINATE.md`); прямая укладка без смещения не поддерживается; невыполнимая схема
сообщается пользователю с причиной.
**Уточнено:** 2026-10-25, после аудита модели (этап 3.0а, модель 1.1).

## D-017 · 2026-10-25 · Ламинат: зазор у стен и пропил (модель 2.0-а)

**Решение:** укладывается поле комнаты за вычетом зазора у обеих стен (`R − 2g`, `D − 2g`); пропил учитывается только
там, где из доски получают две использованные части (пара `s + e + k ≤ l`, естественный обрезок `l − e − k`, куски
короткого ряда), а не прибавляется к каждой доске. Значения по умолчанию — зазор 8 мм, пропил 3 мм — расчётные
предположения, а не требования покрытий. Ряды и пары считаются в целых десятых долях миллиметра, пропил не округляется.
Расчёт по площади — по комнате; отходы в процентах — к площади поля.
**Причина:** этап 3.2б-2 (`docs/calculators/LAMINATE.md` §15): зазор меняет допустимость рядов и число рядов, пропил —
пары отрезков; при `g = k = 0` модель совпадает с 1.2.
**Последствия:** план может быть меньше расчёта по площади — это объясняется пользователю, а не выдаётся за экономию.
С этапа 3.2б-4 значения зазора и пропила вводятся на странице и выводятся в результате; раздельные «пропил»
и «обрезки» не показываются (аудит, `LAMINATE.md` §16).

## D-018 · 2026-10-26 · Штукатурка: расход без значения по умолчанию, масса в BigInt

**Решение:** расход смеси (кг/м² на 1 мм) — обязательное поле без значения по умолчанию; толщина 10 мм в форме —
пример, а не норма. Масса считается в целых единицах `S[мм²] · t₁₀ · c₁₀₀` через `BigInt`, показ — вверх до 0,1 кг,
мешки — от точной массы с запасом.
**Причина:** расход гипсовых и цементных смесей заметно различается, универсальное значение вводило бы в заблуждение;
на пределах полей (50 000 м², 100 мм, 5 кг) произведение превышает 2⁵³ и теряет точность в `number`.
**Последствия:** `BigInt` — встроенный тип, новых зависимостей нет; модель и примеры — `docs/calculators/PLASTER.md`.

## D-019 · 2026-10-26 · Единица измерения в доступном имени поля, отдельный токен рамки полей, subgrid

**Решение:** видимое сокращение единицы («мм») остаётся `aria-hidden`, а в `<label>` добавляется невидимый текст
« (в миллиметрах)» (`src/lib/units.ts`). Рамка полей ввода, списков и поиска — отдельный токен `--color-border-control`
(#858882), `--color-border-strong` не меняется. Поля ряда выравниваются через `subgrid` (подпись + `.field__body`).
**Причина:** сокращение скринридер читает по буквам или пропускает; единица в имени поля озвучивается вместе с ним,
описание (подсказка и ошибка) не меняется, `<label for>` и клик по подписи сохраняются. В скобках — потому что
Chromium добавляет пробел перед абсолютно позиционированным скрытым текстом и запятая давала «Длина , в метрах».
Затемнение общего `--color-border-strong` утяжелило бы декоративные границы; полю нужна граница ≥ 3:1, кнопке с
текстом — нет. `subgrid` с двумя строками не создаёт пустых строк сетки (вариант с четырьмя строками раздувал
промежутки между полями без подсказок до 54 px).
**Последствия:** новая единица требует словесной формы — иначе ошибка сборки; без поддержки `subgrid` остаётся
прежняя раскладка без выравнивания.

## D-020 · 2026-10-26 · Playwright — devDependency, `ui:check` в CI

**Решение:** `playwright@1.63.0` (точная версия) в devDependencies; в CI после сборки —
`npx playwright install --with-deps --only-shell chromium` и `npm run ui:check`. Браузер не кэшируется.
Предпросмотр в `ui-check.mjs` запускается с `--ignore-lock`.
**Причина:** без CI регрессии форм и вёрстки ловились только ручным запуском (аудит, REL-1); глобальный Playwright
не воспроизводим вне облачной среды. 1.63.0 ожидает Chromium сборки 1243 — ту, что предустановлена в облачной
среде, поэтому локальный запуск и CI используют одну версию без загрузки браузера локально; 1.64 потребовала бы
другую сборку. Пакет `playwright`, а не `@playwright/test`: скрипт использует API браузера напрямую.
`chromium.launch()` в режиме headless берёт headless shell — полный Chromium не нужен. Документация Playwright
не рекомендует кэшировать браузеры: восстановление кэша не быстрее загрузки, системные зависимости не кэшируются.
Под ИИ-агентом `astro preview` без флага уходит в фон (его не остановить по pid) и отказывается стартовать при
уже запущенном предпросмотре — отсюда «зависшие» серверы; `--ignore-lock` — документированный одноразовый
запуск в переднем плане.
**Последствия:** обновление Playwright — вместе с проверкой, что браузер нужной сборки доступен в облачной среде
(иначе там понадобится `npx playwright install`); имя job в CI не менялось, чтобы не сломать возможные
обязательные проверки.

## D-021 · 2026-10-26 · Адрес сайта из SITE_URL; robots.txt и sitemap.xml — хуком сборки

**Решение:** `site` в `astro.config.mjs` — из переменной окружения `SITE_URL`, проверенной `parseSiteUrl`
(`https`, без пути, параметров, якоря и логина; иначе сборка падает с объяснением). `robots.txt` и `sitemap.xml`
пишет хук `astro:build:done` встроенной интеграции `src/integrations/seo-files.mjs`; содержимое строят чистые
функции `src/lib/seo.ts` из каталога. Без `SITE_URL` sitemap не создаётся вовсе, robots.txt — без строки `Sitemap`.
**Причина:** статический эндпоинт Astro (`sitemap.xml.ts`) создаёт файл при каждой сборке, а без адреса sitemap
не должно быть совсем — относительные адреса в нём недопустимы. Хук сборки выполняется только при `astro build`,
не требует зависимостей (`@astrojs/sitemap` взял бы страницы из маршрутов, а не из каталога, и добавил бы
зависимость). Код с Node.js (`process.env`, запись файлов) — в отдельном `.mjs`, потому что `astro.config.mjs`
проверяется типами без `@types/node`. `lastmod` не выводится: честной даты изменения страниц нет.
**Последствия:** в `npm run dev` файлов `robots.txt` и `sitemap.xml` нет — только в сборке; на хостинге адрес
задаётся `SITE_URL` в настройках сборки. Open Graph-изображение — статический `public/og.png`, пересоздаётся
`npm run og:image` из шаблона `scripts/og/og-image.html` тем же Playwright, что `ui:check`.

## D-022 · 2026-10-26 · Каталог /kalkulyatory/, «Другие калькуляторы», раздел «Категории» на главной

**Решение:**

- Страница каталога `/kalkulyatory/` — разделы по категориям, только с опубликованными калькуляторами
  (`getCatalogSections`); крошка «Калькуляторы» ведёт на неё.
- Главная и каталог показывают только опубликованные калькуляторы: карточек «Скоро» и обещаний будущих разделов
  на сайте нет (компонент `CalculatorCard` по-прежнему не делает ссылкой неготовую карточку).
- Раздел «Категории» на главной выводится, только если категорий с опубликованными калькуляторами две или больше;
  карточка категории ведёт на `/kalkulyatory/#<id>`. Сейчас такая категория одна — «Ремонт и отделка», — и раздела нет.
- «Другие калькуляторы»: до 4 ссылок (`relatedLimit`), сначала та же категория, затем остальные; внутри групп — по

## D-023 · 2026-10-26 · Ориентиры расхода: медиана марок, разброс покрывает запас; выбор вместо кнопок

**Решение:**

- У полей укрывистости краски и расхода штукатурки и шпаклёвки — выбор «Тип материала» с ориентирами по
  техническим описаниям производителей (не меньше трёх на тип, `docs/research/MATERIAL_PRESETS.md`).
  Значение по умолчанию у поля по-прежнему не задаётся: начальный выбор — «Своё значение (с упаковки)».
- Ориентир — медиана проверенных марок на консервативной стороне: для расхода (кг/м²) — медиана верхних границ,
  вверх до 0,1; для укрывистости (м²/л) — медиана нижних границ, вниз до целого (`presetValueByRule`; тест
  пересчитывает каждое значение). Разброс между марками покрывает поле «Запас», а не сам ориентир; пометка в
  результате показывает его: «Ориентир для …; у разных марок от X до Y — сверьте с упаковкой».
- **Пересмотр (тот же день, до публикации).** Первая версия брала крайнюю границу разброса (самую расходную марку):
  гипсовая штукатурка 1,3, цементная 1,8, финишная шпаклёвка 1,0. Заменено медианой: 1,0 / 1,6 / 0,9; краска (7),
  стартовая шпаклёвка (1,0) и паста (1,7) не изменились.
- Элемент — выпадающий список (`PresetSelect` на основе `SelectField`), а не ряд кнопок.
- Поле расхода остаётся главным: выбор только подставляет число; ручная правка переключает выбор на «Своё
  значение»; формулы и контрольные примеры калькуляторов не меняются.
  **Причина:** без этикетки человек не получал ни одной цифры. Ориентир заведомо приблизителен, и ошибка в меньшую
  сторону дороже: не хватит банки или мешка посреди работы, а лишний мешок можно вернуть или израсходовать.
  Причина пересмотра — двойной запас: крайняя граница уже закладывает худший случай, а поле «Запас» (10 % по
  умолчанию) добавляет его второй раз. Для массовых смесей это переплата: гипсовая штукатурка по 1,3 с запасом —
  1,43 кг на 1 мм при 0,85 у Ротбанда (в 1,7 раза больше). Медиана с запасом (1,1) по-прежнему выше всех
  проверенных марок, кроме одной; округление в сторону большего расхода сохраняет консервативность.
  Выпадающий список на телефоне в магазине — одна строка высотой 44 px и системная прокрутка вариантов одной рукой; три-четыре кнопки с подписями
  «Гипсовая стартовая — 1» не помещаются в строку на 320–390 px и растягивают форму на 2–3 строки.
  **Ограничение проверки:** сеть среды разработки закрыта политикой окружения — страницы производителей не
  открывались; значения взяты из поисковой выдачи по официальным доменам (в основном дословные цитаты
  характеристик). Перед публикацией их стоит сверить по ссылкам из исследования.

## D-024 · 2026-10-26 · Панель итога на телефоне; объявление итога по «Рассчитать» и после паузы ввода

**Решение:**

- На экране уже 960 px после первого успешного расчёта внизу закрепляется панель итога — когда главный итог
  (`.calc-result__main`) вне экрана; в ошибках — «Исправьте значения в полях», пока сообщение об ошибках вне экрана.
  Вся панель — кнопка «К результату»: прокрутка к результату (плавная, без неё при `prefers-reduced-motion`) и фокус
  на его заголовке. «Сбросить» скрывает панель. Реализована один раз — в `calculator-form.ts` и `CalculatorResult`;
  страница только передаёт короткий итог одной строкой `view.summary(…)` в своём `render`.
- Когда показывать — чистая функция `resultBarView` (`src/lib/result-bar.ts`, тесты). IntersectionObserver только
  будит пересчёт; видимость итога считается по его прямоугольнику той же функцией с теми же полями (под шапкой
  64 px, над панелью 80 px), что и `rootMargin`: иначе после «Рассчитать» панель мелькала бы на кадр, пока
  наблюдатель не сообщил о показанном итоге.
- Экранная клавиатура: пока она открыта, панели нет (`keyboardLikelyOpen`: фокус в текстовом поле и видимая область
  `visualViewport` × масштаб ниже 75 % наибольшей высоты окна при той же ширине — так ловится и уменьшение окна на
  старых Android). Поднимать панель над клавиатурой не стали: видимая область при клавиатуре — около 400 px,
  браузер прокручивает поле к краю клавиатуры и панель не учитывает, поле оказалось бы под ней. Новый итог виден
  в панели сразу после закрытия клавиатуры.
- Пока панель видна, у страницы отступ снизу и `scroll-padding-bottom` по фактической высоте панели
  (`--result-bar-space`: на 320 px итог может занять две строки) с `env(safe-area-inset-bottom)`. Браузер при
  переходе фокуса (Tab, «Далее») прокручивает только к краю окна и `scroll-padding` для этого не учитывает (проверено
  в Chromium), поэтому после перехода фокуса механизм сам прокручивает элемент формы выше панели.
- Объявление итога: `role="status"` снят с числа на всех страницах — при живом пересчёте диктор зачитывал итог на
  каждое нажатие клавиши. Вместо него — скрытая область `[data-result-announce]` в `CalculatorResult`: итог
  («Результат: 11,9 л краски · 5 банок») объявляется по «Рассчитать» и после паузы ввода 1 с, если изменился;
  в ошибках — «Расчёт не выполнен: исправьте значения в полях.». Панель — не live-регион.
  **Причина:** на телефоне форма выше экрана, и после первого расчёта итог уходит вниз — правка параметра не видна
  без прокрутки туда и обратно (аудит, UX-1). Объявление на каждое нажатие мешает вводить и перебивает чтение
  поля; пауза 1 с — обычная пауза между числами при наборе.
  **Ограничения:** клавиатуру Android и iOS в среде разработки проверить нельзя — эмулируется только уменьшение окна
  (старые Android). `viewport-fit=cover` в `<meta name="viewport">` не добавлен: это сдвинуло бы весь сайт под
  вырез экрана в альбомной ориентации; без него iOS может отдавать `env(safe-area-inset-bottom)` = 0 — проверить на
  iPhone перед публикацией.

## D-025 · 2026-10-26 · Режим «помещение» в шпаклёвке и штукатурке; потолок — только у шпаклёвки

**Решение:**

- В шпаклёвке и штукатурке выбор «Считать: помещение / отдельные стены», по умолчанию — помещение (как у краски
  и обоев). Помещение: `2 × (длина + ширина) × высота − проёмы`. Режим «отдельные стены» — прежняя модель 1 без
  изменений: функция расчёта без `mode` считает стены, старые контрольные примеры и тесты не менялись (модель 2,
  PUTTY.md, PLASTER.md).
- Поля помещения называются как у краски и обоев — `roomLength`, `roomWidth`, `wallHeight`: по этим именам размеры
  комнаты переходят между калькуляторами. `wallHeight` общий для обоих режимов («Высота стен»).
- Поля другого режима скрываются общим механизмом форм (`data-show-when="mode=room"` у `NumberField` и
  `SelectField`) и не разбираются: текст в скрытом поле не мешает расчёту.
- «Потолок» — только у шпаклёвки: потолок обычно шпаклюют той же смесью и в те же слои, что и стены, перед покраской.
  У штукатурки его нет: допустимая толщина слоя на потолке обычно меньше, чем на стенах, а калькулятор берёт одну
  среднюю толщину на все поверхности — общая масса стен и потолка с одной толщиной была бы неверной. Потолок
  штукатурки считают отдельно (режим «стены», длина × ширина, своя толщина) — это сказано на странице.
  **Причина:** ремонт комнаты — несколько калькуляторов подряд; «стена × число одинаковых стен» требовало пересчитывать
  комнату в стены и вводить размеры в другом виде, чем в краске и обоях.

## D-026 · 2026-10-26 · Размеры комнаты между калькуляторами — в localStorage, только три числа

**Решение:**

- После успешного расчёта «по помещению» (обои, ламинат, краска; шпаклёвка и штукатурка в режиме «помещение»)
  длина, ширина и высота стен сохраняются в `localStorage` под ключом `domraschet:room` в формате
  `{"v":1,"roomLength":4,"roomWidth":3,"wallHeight":2.7}`. Ламинат обновляет длину и ширину, высота из прошлого
  расчёта остаётся. Расчёт отдельной стены ничего не меняет. Плитка не участвует: её поля — стена или пол, а не
  комната.
- При открытии калькулятора сохранённое подставляется только в видимые пустые поля, над формой — строка «Размеры
  комнаты подставлены из прошлого расчёта: 4 × 3 × 2,7 м · Очистить». «Очистить» удаляет запись и очищает
  подставленные поля, которые с тех пор не правили. Расчёт сам не запускается.
- Логика — чистые функции `src/lib/room-memory.ts` (тесты); чтение и запись — в общем `calculator-form.ts`, каждое
  обращение к хранилищу в `try/catch`: без хранилища (приватный режим, запрет) сайт работает как раньше.
  Запись другой версии формата не читается.
  **Почему это не персональные данные (по моей оценке, не юридическое заключение):** три числа без имени,
  адреса, идентификатора устройства или пользователя; по ним нельзя определить человека (152-ФЗ, ст. 3: персональные
  данные — информация, относящаяся к прямо или косвенно определённому лицу). Данные не покидают устройство:
  сайт статический, серверной части и аналитики нет, на сервер они не отправляются и в ссылки не попадают (ссылка
  на расчёт — только по кнопке, D-027).
  **Почему без уведомления о cookie:** cookie не используются; российское законодательство отдельного баннера для
  хранения на устройстве не требует. **Сомнение:** правила ЕС (ePrivacy, ст. 5(3)) разрешают хранить данные
  на устройстве без согласия, только если это строго необходимо для услуги, которую человек запросил;
  запоминание размеров — удобство, и при строгом прочтении для посетителей из ЕС может понадобиться уведомление.
  Решение перед публикацией — за владельцем сайта; самое простое — упомянуть запоминание и «Очистить» на странице
  «О сервисе».

## D-027 · 2026-10-26 · Ссылка на расчёт: `?v=1` и имена полей; копирование итога

**Решение:**

- В результате после расчёта — «Ссылка на расчёт» и «Скопировать итог» (`CalculatorResult`, без JavaScript скрыты).
  Ссылка — адрес страницы с параметрами `?v=1&<имя поля>=<значение>`: только видимые поля формы и выбор типа
  материала; числа с точкой (`wallHeight=2.7`), пустое поле — пустым значением (`reserve=`): иначе при открытии там
  оказалось бы значение по умолчанию и ссылка зависела бы от его будущих изменений. Выбор «Своё значение» (пустой)
  не передаётся — он и так по умолчанию.
- Открытие ссылки заполняет форму (сначала выборы — от режима зависит, какие поля видны) и сразу считает, без
  переноса фокуса и прокрутки: на телефоне итог видно в панели итога. Значения ссылки важнее сохранённых размеров
  комнаты: при ссылке размеры из памяти не подставляются (`startValues`). Без `v=1` параметры не читаются; неизвестные
  параметры, текст вместо числа, несуществующий вариант и значения длиннее 32 символов молча пропускаются, остальное
  проверяет калькулятор как обычный ввод. Адрес страницы после открытия не переписывается.
- «Ссылка на расчёт»: на сенсорном экране (`pointer: coarse`) с `navigator.share` — системное меню «Поделиться»,
  иначе копирование в буфер. «Скопировать итог» — название калькулятора, ключевые параметры и «К покупке» из
  `view.report(…)` страницы (тот же результат, что на экране) и ссылка. Подтверждение «Скопировано» —
  `role="status"` рядом с кнопками, через 3 с убирается молча. Буфер недоступен — текст в поле, в фокусе и
  выделен для копирования вручную.
- Разбор и сборка ссылки, текст итога — чистые функции `src/lib/share-link.ts` (тесты, круговая проверка).
- SEO: страницы статические — canonical и `og:url` собираются из пути без параметров; страницы с параметрами
  в sitemap не добавляются. Проверено на собранной странице и в `ui:check` со `SITE_URL`.
  **Причина:** расчёт нужно отправить бригаде или показать в магазине; адрес с параметрами работает в любом
  мессенджере и не требует сервера и хранения на нём.

## D-028 · 2026-10-26 · Фокус в режиме высокой контрастности: прозрачный outline вместо `outline: none`

**Решение:** во всех собственных стилях фокуса (общий `:focus-visible` в `global.css` — ссылки, кнопки, «Очистить»,
кнопки ссылки, поле копирования; `NumberField`, `SelectField`, поиск каталога, панель итога) `outline: none` заменён
на `outline: 2px solid transparent` с отступом. В обычном режиме outline не виден — фокус по-прежнему рисует тень
`--focus-ring`; в режиме `forced-colors` (высокая контрастность Windows) тени отключаются, а цвет outline браузер
заменяет системным — рамка видна. Попутно: линии значка «Меню» нарисованы фоном и в этом режиме пропадали —
им дан `forced-color-adjust: none`. Отдельное правило `@media (forced-colors: active)` для фокуса не понадобилось.
**Проверка:** в Chromium с эмуляцией `forcedColors: 'active'` у `outline: none` вычисленный стиль — `none` и тень
`none` (фокуса не видно), у прозрачного outline — `solid 2px` системного цвета; `ui:check` проверяет это для
каждого типа элементов. Настоящий режим высокой контрастности Windows в среде разработки недоступен.

## D-029 · 2026-10-26 · Свои веб-шрифты Onest и JetBrains Mono вместо системных

**Решение:** вместо системных шрифтов (D-005) — Onest (текст и заголовки, 400/600/800) и JetBrains Mono (числа,

  `public/fonts/OFL-Onest.txt` и `OFL-JetBrainsMono.txt`.
- **Вес:** 10 файлов, 120 236 байт (117,4 КиБ) при бюджете 150 КБ (проверка в `ui:check`). Знак рубля «₽» и
  математические знаки (⌈ ⌉ ≈) не входят в подмножества — для них используется запасной шрифт.

  `unicode-range: U+20BD`, грузятся только на страницах с «₽»): всего 15 файлов, 123 520 байт (120,6 КиБ).
  **Дополнение (0.17.1):** знаки формул и кнопок Σ → ≈ ≤ ⌈ ⌉ ⌊ ⌋ ✓, найденные скриптом по собранным страницам, —

## D-034 · 2026-10-31 · Хостинг REG.RU, выкладка по SSH из GitHub Actions, настройки Apache

**Решение:** сайт `konturix.ru` выкладывается на виртуальный хостинг REG.RU (Linux, Apache) из GitHub Actions
(`.github/workflows/deploy.yml`, инструкция — `docs/DEPLOY.md`). Хостинг и домен выбрал пользователь.

- **Когда:** push в `main` (после слияния) и вручную; выкладывается только ветка `main`. Сначала задача
  «Проверки и сборка»: `npm run check` и `ui:check` с `SITE_URL` из переменной репозитория (пустая — остановка),
  `dist/` — артефактом; потом «Выкладка» — только после её успеха. Секреты есть только у задачи выкладки.
  `concurrency` — одна выкладка за раз, идущая не отменяется (оборванный `rsync --delete` оставил бы полсайта).
  Проверки — свои, а не вызов CI: выкладке нужен один режим (боевой адрес), CI проверяет оба.
- **Как копировать:** `rsync --delete` по SSH, а если на сервере нет rsync (в справке REG.RU об этом ничего
  нет) — автоматически зеркалирование по SFTP: `lftp mirror -R --delete`. rsync лучше: передаёт только
  изменения, `--delay-updates` подменяет файлы в конце, права задаются явно (`--chmod=D755,F644`). SFTP есть на
  любом хостинге с SSH. Папка `.well-known/` на сервере не удаляется: туда хостинг кладёт файлы для SSL.
- **Вход:** по SSH-ключу (рекомендация REG.RU; отдельный ключ только для выкладки), пароль — запасной вариант
  через `sshpass` из переменной окружения. Подпись сервера — из секрета `DEPLOY_KNOWN_HOSTS`,
  `StrictHostKeyChecking=yes`. Логика — `scripts/deploy.sh` (а не в YAML), чтобы её можно было проверить
  локально: проверены ключ и пароль, rsync и SFTP, автовыбор, защита от пустой сборки и неверного пути.
- **Защита от пустой выкладки:** без `index.html`, `404.html`, `.htaccess`, `robots.txt`, `sitemap.xml` или с менее
  чем 2 страницами, с путём не от корня, слишком коротким или с «..» — остановка до копирования.
- **`public/.htaccess`:**
  - один 301-переход к каноническому адресу (https, без www, слэш на конце папки) — без цепочек;
  - HTTPS определяется по `%{HTTPS}` и по `X-Forwarded-Proto` (на хостинге перед Apache может стоять nginx;
    иначе — бесконечная переадресация). Подмена этого заголовка лишь отменяет переход для самого клиента;
  - домен берётся из запроса без «www.» — файл не привязан к домену;
  - `ErrorDocument 404 /404.html`; папки без страницы (`/_astro/`, `/fonts/`) — 404 через `mod_rewrite`,
    а не `Options -Indexes`: если хостинг запрещает менять Options, та строка дала бы 500 на всём сайте;
  - кэш: `/_astro/` и `/fonts/` — год, `immutable` (у `/_astro/` хеш в имени; шрифт с новым содержимым —
    только под новым именем), HTML, `sitemap.xml`, `robots.txt` — `no-cache`; сжатие `mod_deflate`; `utf-8`;
  - `X-Content-Type-Options: nosniff`, `Referrer-Policy: strict-origin-when-cross-origin`.
- **Content-Security-Policy — отложена:** на страницах есть встроенные скрипты (меню — модуль, небольшой
  классический скрипт) и стили, которые Astro вставляет в HTML. Строгая политика потребует хешей, пересчитываемых
  при каждой сборке (или `'unsafe-inline'`, что лишает её смысла); ошибка в ней ломает меню и калькуляторы молча.
  Вернуться после первой выкладки: собирать хеши хуком сборки и проверять в `ui:check` отсутствие нарушений.
  **Причина:** статический сайт без серверной части — достаточно копирования файлов; проверки перед выкладкой те
  же, что в CI, с боевым адресом. **Проверено локально** на Apache 2.4 и SSH-сервере (`docs/DEPLOY.md`); на REG.RU —
  после добавления секретов. **Не проверено:** `actionlint` (не установлен в среде) — вместо него разбор YAML
  и `shellcheck` всех `run:` и `scripts/deploy.sh`.

## D-033 · 2026-10-30 · Стоимость по упаковкам во всех калькуляторах

**Решение:** у всех шести калькуляторов — необязательная цена и стоимость.

- **Цена — как на ценнике**, стоимость — **по тому, что реально покупается**: целые банки, мешки, упаковки,
  рулоны, а не точный расход (5 банок × 2 380 ₽, а не 12,7 л × цену литра). Мы не даём и не подсказываем цен —
  только то, что ввёл пользователь. Без цены результат как раньше.
- Если без размера упаковки стоимость не посчитать (краска без объёма банки, шпаклёвка и штукатурка без массы,
  плитка «за упаковку» без числа плиток в упаковке), у поля цены — подсказка «Укажите … — тогда посчитаем
  стоимость». Это не ошибка: количество считается как обычно.
- **Плитка — выбор единицы цены**: «за м²» по умолчанию (так пишут на ценниках плитки) или «за упаковку». За м² —
  купленная площадь `упаковки · плиток в упаковке · a · b`, без числа в упаковке — `плитки с запасом · a · b`;
  площадь плитки — номинальная, без шва (так считает магазин). Округление до копейки — половина вверх.
- **Точность:** цена 0–1 000 000 ₽, не точнее копейки (раньше у обоев и ламината копейки сверх двух знаков молча
  округлялись — теперь ошибка у поля, как везде); внутри — целые копейки, произведения в `BigInt`; сумма больше
  2⁵³ − 1 копеек — ошибка у цены, а не неточное число (достижимо только в предельном вводе плитки за упаковку).
- Одна общая функция `src/lib/cost.ts` (проверка цены, копейки, стоимость упаковок и площади, разбивка, текст)
  и два общих компонента: `CostGroup` — группа «Стоимость · необязательно» в конце формы, `CostLine` — строка
  «Стоимость ≈ 11 900 ₽» с разбивкой «5 банок × 2 380 ₽» сразу под «К покупке». Стоимость — в «Скопировать»,
  в ссылке на расчёт (цена — обычное поле формы) и в панели итога, если помещается в две строки.
- Цена не запоминается между калькуляторами (материалы разные): в `localStorage` — только размеры комнаты (D-026).
  Имена полей обоев и ламината (`rollPrice`, `packPrice`) не менялись — старые ссылки работают.
  **Причина:** покупатель платит за упаковки, а не за литры; стоимость по точному расходу занижала бы сумму.
  **Альтернативы:** цена за литр/килограмм — на ценниках её нет, пользователю пришлось бы пересчитывать;
  справочные цены — устаревают и были бы рекламой магазинов.

## D-032 · 2026-10-27 · Живая схема над формой

**Решение:** над формой шести калькуляторов — схема, которая перерисовывается при вводе (`docs/SCHEMATIC.md`):
план помещения с размерными линиями, «h = …» и площадью стен (обои, краска, шпаклёвка, штукатурка), развёртка
стены в режиме «отдельные стены», план с рядами досок и стыками (ламинат), поверхность с сеткой плиток (плитка).

- Геометрия — чистая функция `schematicModel` в `src/lib/schematic.ts` по **тексту полей**, а не по результату
  расчёта: схема живёт и до «Рассчитать», и при ошибке в другом поле. Значение вне пределов калькулятора на схеме
  не появляется (подпись «длина»), ошибки по-прежнему показывает форма. Площадь — через целые миллиметры, как
  в калькуляторах. Разметка SVG — строкой (`schematicSvg`), одной функцией для сборки (заготовка без JavaScript)
  и браузера (перерисовка): двух реализаций рисунка нет.
- Пропорция ограничена 4:1; длиннее — условный разрыв (зигзаг) на длинных сторонах, подпись размера настоящая.
  Табличка примечаний — внутри, сбоку или поверх; при мелкой плитке — каждая k-я линия сетки с пометкой.
- Доступность: `role="img"` и `aria-label` с размерами словами («длина 4, ширина 3…»). Подпись меняется при вводе,
  но не объявляется — это не live-регион; итог диктору объявляется, как прежде (D-024).
- Схема компактная (SVG 300 × 150, до 26rem): первое поле формы остаётся на первом экране 390 × 844.
  **Причина:** схема — сигнатурный элемент «Чертежа»: видно, что именно посчитано, ошибки в размерах заметны
  до расчёта. **Альтернативы:** схема по результату расчёта — не видна до «Рассчитать» и при ошибках; canvas — нет
  доступной подписи и масштабирования; библиотека графики — лишняя зависимость ради прямоугольников и линий.

  «Список покупок · <калькулятор> (ДомРасчёт)», позиция «□ …» (отметить в магазине), исходные данные строками

- «Дальше для этой комнаты» — список из каталога по новому полю `roomFields` (какие размеры комнаты калькулятор

  размеры действительно сохранены (чтение из хранилища после записи); при запрещённом хранилище её нет.
  **Причина:** итог читается как список к покупке, а не как набор чисел; расчёт прозрачен — каждая цифра с
  выноской. Блок «Дальше» продолжает ремонт комнаты без повторного ввода размеров.
- **Дополнение (0.17.1, после просмотра на iPhone):** «К покупке» — то, что покупают: если указан объём упаковки
  (банка, мешок, упаковка), главная цифра — число упаковок с подписью («1 банка по 30 л», «23 мешка по 25 кг»,
  «18 упаковок по 11 шт.»), под ней — «нужно 26,8 л»; без объёма — литры и килограммы, как раньше. Правило —
  чистая функция `packagePurchase` (`src/lib/purchase.ts`) с тестами, склонения — `plural.ts`; по нему же панель
  итога, объявление диктору и строка «Скопировать» («□ 23 мешка по 25 кг — нужно 568,4 кг»). Отдельная строка
  `.calc-result__cost` с банками убрана: сколько это в упаковках — последней строкой «Как получилось»
  («5 × 2,7 л = 13,5 л»). Обои и ламинат уже считали рулоны и упаковки — не менялись. Подписи вычитаний — без
  двойного отрицания: «Окна и двери» со значением «−5 м²» (диктор слышит «минус» из знака). Справка об ориентире
  — нейтральная; оранжевый в результате — только вычитание и предупреждение о нетипичном значении. Единицы в
  строках результата — Onest, числа — JetBrains Mono.
